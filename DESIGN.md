# Дизайн-документация портала самообслуживания

Этот проект содержит HTML и CSS для нескольких стендов портала самообслуживания. Код не является полноценным frontend-приложением: это набор шаблонов и стилей, которые вставляются в платформу self-service и используют ее теги, Liquid-переменные, иконки и данные.

Главная цель проекта — поддерживать одинаковую верстку и поведение между средами, не смешивая ссылки на изображения.

## Структура проекта

```text
portal-fix/
  Demo/
    index.html
    style.css
  Staging/
    index.html
    style.css
  Prod/
    index.html
    style.css
  MosITSM/
    index.html
    style.css
  DESIGN.md
```

## Среды

`Demo/` — версия для demo-стенда.

`Staging/` — версия для staging-стенда.

`Prod/` — версия для production-стенда. Верстка и CSS синхронны с остальными средами; `src` у картинок в `Prod/index.html` — отдельный prod-набор.

`MosITSM/` — версия для MosITSM-стенда. Верстка и CSS синхронны с остальными средами; `src` у картинок в `MosITSM/index.html` — отдельный MosITSM-набор.

Файлы `Demo`, `Staging`, `Prod` и `MosITSM` должны развиваться параллельно по логике, разметке и CSS. Если меняется логика, разметка или визуальное правило, обычно это нужно применить во всех средах, кроме случаев ниже.

Исключение: ссылки на изображения.

## Неприкосновенное правило по изображениям

Ссылки на изображения уникальны для каждой среды. Их нельзя:

- заменять на ссылки из другой среды;
- автоматически унифицировать;
- синхронизировать между `Demo`, `Staging`, `Prod` и `MosITSM`;
- “чинить” без отдельного прямого указания.

То же правило в обратную сторону: asset URL каждой среды остаются в своей папке.

Примеры demo-ссылок начинаются с:

```text
https://ec6a1843-6193-40fc-9c40-978edc39ddb2.selstorage.ru/instances/rrt1/media/...
```

Примеры staging-ссылок начинаются с:

```text
https://3b5990f3-9a6c-4324-b033-865158d474ce.selstorage.ru/media/...
```

Примеры prod-ссылок начинаются с:

```text
https://e90a501f-8913-4baa-a8dd-3c302cdc9c79.selstorage.ru/media/108/...
```

Примеры MosITSM-ссылок — тот же бакет, другой media-префикс:

```text
https://e90a501f-8913-4baa-a8dd-3c302cdc9c79.selstorage.ru/media/135/...
```

В `Prod/index.html` и `MosITSM/index.html` по шесть статических `<img>` (header + hero) с одинаковой разметкой, но разными URL:

| Класс | Файл |
|-------|------|
| `.brand-logo-img` | `р-сервис.svg` |
| `.hero-visual-img` | `photo_2026-06-05_11-34-34 (2).jpg` |
| `.hero-logo-badge-img` | `photo_2026-06-05_11-34-34 (2).jpg` |
| `.hero-service-img--enterprise` | `enterprise.png` |
| `.hero-service-img--provider` | `service-provider.png` |
| `.hero-service-img--government` | `government1.png` |

Перед любыми изменениями, затрагивающими HTML, нужно помнить: `src` у картинок в `Demo/index.html`, `Staging/index.html`, `Prod/index.html` и `MosITSM/index.html` не трогать без явной задачи на конкретную среду.

## Что находится в HTML

HTML использует компоненты платформы:

- `self-service-header`
- `self-service-homepage`
- `self-service-search`
- `self-service-user-statistics`
- `self-service-nav`
- `self-service-color-mode-picker`

Внутри шаблона используются Liquid-переменные и условия:

- `{{ user.name }}`
- `{{ user.avatar.url }}`
- `{{ count.shopping_cart }}`
- `{{ record.subject }}`
- `{% if ... %}`
- `{% for ... %}`

Это означает, что HTML нельзя воспринимать как статическую страницу. Часть данных приходит из платформы во время рендера.

### Service Catalog

Раздел “Каталог” оформляется логически так же, как разделы “Оповещения” и “База знаний”: широкий kicker-пояс на всю ширину секции, крупный заголовок, подзаголовок и затем содержимое раздела.

Внутри раздела первыми элементами могут находиться shortcuts «Мои услуги» и избранное. Они не должны быть отдельными псевдовиджетами между секциями. В HTML оба живут внутри `.rsvc-service-catalog-hub` в обёртке `.rsvc-service-catalog-shortcuts` (сетка из двух колонок, на мобилке тоже в один ряд).

Каждый shortcut — `.my-services-widget` внутри `.rsvc-service-catalog-shortcut`. Показ: `nav.services.visible` и/или `nav.favorites.visible`. Если виден только один shortcut, он растягивается на всю ширину ряда.

После shortcut идут списки шаблонов запросов:

- недавно использованные;
- часто используют;
- новые шаблоны.

Ключевые классы:

- `.rsvc-service-catalog-hub`
- `.rsvc-service-catalog-shortcuts`
- `.rsvc-service-catalog-shortcut`
- `.my-services-widget`
- `.my-services-widget__icon`
- `.my-services-widget__title`
- `.my-services-widget__description`
- `.my-services-widget__arrow`
- `.rsvc-template-panel`
- `.rsvc-template-panel--recent`
- `.rsvc-template-panel--popular`
- `.rsvc-template-panel--latest`
- `.rsvc-mini-list`
- `.rsvc-list-icons`
- `.rsvc-list-copy`
- `.rsvc-list-date`
- `.rsvc-popularity-badge`

Правило дизайна: элементы списков должны выглядеть как единые карточки с обводкой и скруглением, а не как строки с простыми разделителями.

Счетчик популярности должен находиться рядом с иконкой, а не в конце заголовка.

Условие показа каталога должно учитывать не только наличие шаблонов, но и `nav.services.visible`, чтобы раздел мог отобразить shortcut “Мои услуги”, даже если списки шаблонов пустые.

Старый внешний блок `.widgets--my-services-shortcut` считается legacy-слоем. Новую разметку для отдельного псевдовиджета “Мои услуги” перед каталогом добавлять не нужно.

### Broadcasts

Раздел “Оповещения” показывает важные сообщения и объявления через штатный `self-service-carousel`.

Ключевые классы:

- `.rsvc-broadcast-hub`
- `.rsvc-broadcast-carousel`
- `.rsvc-broadcast-card`
- `.rsvc-broadcast-icon`
- `.rsvc-broadcast-body`
- `.rsvc-broadcast-btn`

Правило дизайна: в светлой теме карточка оповещения должна быть светлой matte-карточкой, а не темной градиентной панелью.

Счетчик количества оповещений `.rsvc-section-count` располагается справа от строки заголовка.

Не добавлять кастомные стрелки, счетчики вида `1 из 5` или самописную логику перелистывания без подтвержденного API платформенного `self-service-carousel`. Штатные точки пагинации остаются системным поведением.

### Workspace Widgets

Рабочие списочные виджеты: входящие, ожидания, открытые запросы, согласования, активы, завершённые запросы.

Ссылки «Все» в заголовках виджетов ведут на разделы навигации, а не на устаревшие подразделы списков:

- входящие → `nav.inbox.url`
- ждут моего действия → без ссылки “Все”, только счётчик и список `list.requests_waiting_for_me`
- открытые запросы → `nav.requests.url` + `?view_state=open`
- завершённые запросы → `nav.requests.url` + `?view_state=completed`
- согласования → `nav.approvals.url`
- активы → `nav.assets.url`

Ключевые классы:

- `.rsvc-workspace-widgets`
- `.rsvc-workspace-grid`
- `.rsvc-widget-panel`
- `.rsvc-widget-panel--accent`
- `.rsvc-mini-list`
- `.rsvc-list-icons`
- `.rsvc-list-copy`
- `.rsvc-asset-avatar`

Эти виджеты являются основным визуальным эталоном для списков. Если другой списочный блок выглядит иначе, его нужно приводить к этим правилам.

## Общая дизайн-система

### Визуальный стиль

Основной стиль интерфейса — спокойные рабочие панели:

- светлая тема: белые/почти белые matte-поверхности;
- темная тема: глубокие темные панели без лишних вторых контуров;
- акцентный цвет: бирюзовый/циан;
- карточки списков имеют тонкую обводку, мягкую тень и скругление;
- декоративные blur/glow-эффекты должны быть умеренными.

Фон страницы должен быть профессиональной matte-поверхностью:

- светлая тема: нейтральный вертикальный градиент `#f6fafb → #eef3f5`;
- поверх фона — очень тонкая сетка с низкой прозрачностью;
- бирюзовое свечение используется только как слабый акцент, а не как основной цвет страницы;
- темная тема использует ту же логику: глубокий matte-фон, едва заметная сетка и мягкие cyan/mint акценты.

Светлая и темная темы должны ощущаться парой: структура фона совпадает, отличается только яркость и плотность поверхности.

### Заголовки Секций

Секции верхнего уровня используют общий паттерн:

- `.widgets-section-kicker` как полноширинный пояс на всю ширину контента секции;
- `.widgets-section-title` обычного секционного размера, без hero-масштаба;
- `.rsvc-section-subtitle` сразу под заголовком;
- содержимое секции ниже заголовочной зоны.

Такой паттерн обязателен как минимум для:

- “Каталог”;
- “Оповещения”;
- “Рабочая зона”;
- “База знаний”.

Полноширинные kicker-полосы “Оповещения” и “Рабочая зона” должны использовать прозрачную акцентную поверхность в тёмной теме, чтобы фоновая сетка читалась так же, как у соседних секционных полос.

Не возвращать короткие капсулы-kicker для этих секций, если задача явно не требует другого дизайна.

### Списочные виджеты

Все списочные виджеты должны придерживаться одного паттерна:

- внешний контейнер `.rsvc-widget-panel`;
- список `.rsvc-mini-list` или специализированный список на его основе;
- элемент списка как карточка;
- иконка слева;
- текст в `.rsvc-list-copy`;
- счетчик, дата или мета-информация либо рядом с иконкой, либо в выделенной правой колонке;
- скругление элементов списка;
- единый hover.

На мобильных ширинах заголовки рабочих виджетов не должны переноситься внутри слова. Шапка `.rsvc-widget-panel-header` в `.rsvc-workspace-widgets` держит область заголовка и actions в одной строке: слева kicker/`h3`, справа счётчик и ссылка “Все” в выделенной компактной колонке. `h3` использует обычные переносы по словам без `overflow-wrap: anywhere`.

Не нужно возвращаться к варианту, где элементы разделены только линиями без карточной обводки.

### Отступы

Крупные секции используют компактный вертикальный ритм. Между блоками не должно быть огромных пустых провалов.

Особенно важны:

- `.rsvc-service-catalog-hub`
- `.rsvc-service-catalog-shortcut`
- `.rsvc-knowledge-hub`
- `.rsvc-workspace-widgets`

### Темная тема

Темная тема управляется через:

```css
:host([data-color-mode='dark']) ...
```

Светлая тема часто задается через:

```css
:host(:not([data-color-mode='dark'])) ...
```

Если добавляется финальный override для светлой темы, нужно проверить, не нужен ли аналогичный override для темной темы.

## CSS-организация

Файл CSS большой и исторически накопленный. В нем есть ранние базовые правила и поздние финальные переопределения.

Практическое правило:

- сначала ищем существующий паттерн;
- не создаем новую дизайн-систему;
- новые правки добавляем точечно;
- финальные overrides допустимы, если нужно перебить старое правило без риска сломать большую часть файла;
- не использовать `!important`, если можно обойтись специфичностью и порядком правил.

Важные финальные области CSS:

- правила для knowledge articles;
- правила для popular templates;
- единый вид catalog template panels;
- размещение shortcut “Мои услуги” внутри каталога;
- matte-слой для workspace widgets;
- matte-слой для knowledge base;
- одинарный контур usage overview.

В самом конце `Demo/style.css`, `Staging/style.css`, `Prod/style.css` и `MosITSM/style.css` есть блок `Final stability layer`. Его нужно держать последним. Он фиксирует правила, которые должны гарантированно победить старые накопленные стили: заголовок каталога, полноширинный kicker “База знаний”, строки каталога, размещение shortcut “Мои услуги”, usage overview, broadcast-карточку в светлой теме, положение broadcast-счетчика и прозрачный фон quick-actions.

## Как безопасно вносить изменения

1. Определить, относится ли изменение ко всем средам.
2. Если да — внести одинаковую правку в `Demo`, `Staging`, `Prod` и `MosITSM` (для CSS/HTML).
3. Не менять ссылки на изображения в `Staging`, если задача не про staging-assets.
4. Не менять ссылки на изображения в `Demo`, если задача не про demo-assets.
5. Не менять ссылки на изображения в `Prod`, если задача не про prod-assets.
6. Не менять ссылки на изображения в `MosITSM`, если задача не про MosITSM-assets.
7. Проверить, что классы и Liquid-переменные не сломаны.
8. Проверить светлую и темную тему.
9. Проверить desktop и mobile.
10. После любой правки дизайна, верстки, токенов, тем или структуры секций актуализировать `DESIGN.md` сразу, без отдельного запроса пользователя.

Рабочее правило для агента: `DESIGN.md` является живой дизайн-докой проекта. Если меняется внешний вид, структура HTML/CSS, правила темы, токены или договоренности по поддержке сред, нужно обновить документацию в том же проходе.

## Что нельзя делать

- Нельзя автоматически заменять asset URL между средами.
- Нельзя удалять Liquid-условия и циклы без понимания данных платформы.
- Нельзя переименовывать платформенные custom tags.
- Нельзя изобретать новую структуру компонентов, если существующий паттерн уже есть.
- Нельзя править только одну среду, если изменение касается общей верстки/CSS и не связано с environment-only assets.

## Бейджи среды

Небоевые стенды должны быть визуально промаркированы, чтобы пользователи не путали их с production.

- `Demo/index.html` содержит `.rsvc-environment-badge.rsvc-environment-badge--demo` с видимой подписью `Demo-среда`.
- `Staging/index.html` содержит `.rsvc-environment-badge.rsvc-environment-badge--staging` с видимой подписью `Staging-среда`.
- `Prod/index.html` и `MosITSM/index.html` не должны содержать environment-бейдж без отдельного явного требования.
- HTML-маркер бейджа размещается внутри `<self-service-header>`, потому что платформа разрешает на верхнем уровне только `self-service-*` элементы.
- CSS бейджа синхронизируется во всех `style.css`, но отображается только там, где есть HTML-маркер.
- Бейдж фиксируется в правом верхнем углу контента под sticky-шапкой, использует `pointer-events: none` и не должен забирать клики у элементов шапки.
- На мобильных бейдж переключается на короткую подпись (`Demo` / `Staging`), чтобы не перекрывать контент.

## Короткое резюме

Проект — это параллельные версии одного портала: `Demo`, `Staging`, `Prod`, `MosITSM`.

Верстка и стили должны быть синхронными.

Ссылки на изображения должны оставаться разными для каждой среды.

Главный визуальный принцип: единые рабочие списочные виджеты, аккуратные matte-поверхности, одинарные контуры, компактные отступы и поддержка светлой/темной темы.
