# Дизайн-документация портала самообслуживания

Этот проект содержит HTML и CSS для разных пространств (аккаунтов) портала самообслуживания. Код не является полноценным frontend-приложением: это набор шаблонов и стилей, которые вставляются в платформу self-service и используют ее теги, Liquid-переменные, иконки и данные.

Главная цель проекта — поддерживать одинаковый состав страницы, одинаковую верстку, одинаковые виджеты и одинаковое поведение во всех пространствах. Разные пространства могут отличаться только визуальным стилем: цветами, фоном, декоративными эффектами, тенями, радиусами, типографическим настроением и общим ощущением бренда.

## Структура проекта

```text
self service portal only demo/
  Беларусь ИТ/
    index.html
    style.css
  ЦОД/
    index.html
    style.css
  DESIGN.md
```

## Пространства

`Беларусь ИТ/` — дизайн для пространства/аккаунта “Беларусь ИТ”. Сейчас это первый отдельный визуальный слой: светлая/темная тема в стилистике белорусского ИТ-портала, выполненная на чистом CSS без статических ссылок на картинки. Обязательная деталь дизайна — белорусский орнамент на CSS-плате/цифровой поверхности в hero.

`ЦОД/` — дизайн для пространства/аккаунта “ЦОД”. Пока остается базовым вариантом и не меняется при работах над “Беларусь ИТ”, если задача явно не просит обратного.

Каждая папка пространства содержит:

- `index.html` — платформенный шаблон с одинаковым набором элементов;
- `style.css` — визуальная тема конкретного пространства.

## Главное правило пространств

Все элементы, секции, виджеты, Liquid-переменные, условия, циклы, ссылки навигации и платформенные custom tags должны сохраняться в каждом дизайне.

При создании нового дизайна для пространства нельзя удалять, отключать, переименовывать или переставлять функциональные блоки ради визуального отличия. Меняется только красота: визуальная тема и оформление уже существующей структуры.

Если появляется новый функциональный элемент, секция или виджет, его нужно добавить во все пространства. Если меняется логика HTML, условие показа, ссылка или платформа данных, изменение также применяется во все пространства.

В пользовательском интерфейсе каждого пространства нельзя упоминать другое пространство или чужую предметную область. `Беларусь ИТ` не должен называться ЦОД или центром обработки данных; `ЦОД` не должен содержать брендинг или тексты “Беларусь ИТ”.

Различия между пространствами допустимы только в CSS и только на уровне визуального слоя:

- палитра;
- фон страницы;
- поверхности карточек и панелей;
- обводки, тени, свечения;
- радиусы;
- декоративные паттерны;
- состояние светлой и темной темы;
- визуальная обработка уже существующих изображений или замена декоративных статических изображений на CSS-графику.

Для всех CSS-тем действует дополнительное правило качества: элементы не должны пересекаться, прятаться друг за другом или зависеть от отрицательных отступов, которые ломают поток страницы. Декоративные слои всегда находятся за контентом и не перекрывают поиск, карточки, заголовки и списки.

## Правило по изображениям

В старой доке изображения были environment-only asset URL. В текущей модели аккаунтов правило зависит от пространства.

`Беларусь ИТ/` использует чистый CSS для логотипа, hero-графики и декоративных карточек услуг. Статические ссылки на картинки из этого шаблона удалены. Остаются только платформенные изображения из данных, например аватары пользователя и записей.

`ЦОД/` пока сохраняет исходные статические изображения.

Рабочее правило на будущее:

- не менять `src` у статических `<img>` без отдельной задачи;
- не добавлять статические ссылки на картинки в `Беларусь ИТ/`, пока выбранный подход — чистый CSS;
- если для пространства нужны собственные изображения, заменять или добавлять их только в конкретной папке пространства и зафиксировать это в доке;
- Liquid-изображения, например `{{ user.avatar.url }}` и `{{ record.avatar.url }}`, не трогать.

Классы декоративных визуальных элементов:

| Класс | Назначение |
|-------|------------|
| `.brand-logo-mark` | CSS-логотип в шапке “Беларусь ИТ” |
| `.hero-visual-img` | основное изображение hero |
| `.hero-logo-badge-img` | изображение в badge hero |
| `.hero-service-img--enterprise` | карточка enterprise |
| `.hero-service-img--provider` | карточка service provider |
| `.hero-service-img--government` | карточка government |

## Что находится в HTML

HTML использует компоненты платформы:

- `self-service-header`
- `self-service-homepage`
- `self-service-search`
- `self-service-user-statistics`
- `self-service-nav`
- `self-service-color-mode-picker`
- `self-service-carousel`

Внутри шаблона используются Liquid-переменные, условия и циклы:

- `{{ user.name }}`
- `{{ user.avatar.url }}`
- `{{ count.shopping_cart }}`
- `{{ record.subject }}`
- `{% if ... %}`
- `{% for ... %}`

HTML нельзя воспринимать как статическую страницу. Часть данных приходит из платформы во время рендера, поэтому правки должны сохранять платформенные контракты.

## Общая дизайн-система

### Что остается постоянным

Во всех пространствах должны совпадать:

- набор секций;
- порядок секций;
- набор карточек и виджетов;
- Liquid-логика;
- платформенные custom tags;
- навигационные ссылки;
- адаптивное поведение;
- поддержка светлой и темной темы.

### Что можно менять

Для каждого пространства можно создавать отдельное визуальное настроение:

- “Беларусь ИТ” может быть более технологичным, государственным, строгим или корпоративным;
- “ЦОД” может быть более инфраструктурным, инженерным, темным, сеточным или дата-центричным;
- будущие пространства могут получать свои палитры и декоративные мотивы.

Но даже самый разный дизайн должен оставаться тем же порталом по составу и поведению.

### Списочные виджеты

Все списочные виджеты должны придерживаться одного паттерна:

- внешний контейнер `.rsvc-widget-panel`;
- список `.rsvc-mini-list` или специализированный список на его основе;
- элемент списка как карточка;
- иконка слева;
- текст в `.rsvc-list-copy`;
- счетчик, дата или мета-информация рядом с иконкой или в выделенной правой колонке;
- скругление элементов списка;
- единый hover.

Не нужно возвращаться к варианту, где элементы разделены только линиями без карточной обводки.

### Заголовки секций

Секции верхнего уровня используют общий паттерн:

- `.widgets-section-kicker` как пояс/метка секции;
- `.widgets-section-title` обычного секционного размера, без hero-масштаба;
- `.rsvc-section-subtitle` сразу под заголовком;
- содержимое секции ниже заголовочной зоны.

Паттерн обязателен для:

- “Каталог”;
- “Оповещения”;
- “Рабочая зона”;
- “База знаний”.

### Темная тема

Темная тема управляется через:

```css
:host([data-color-mode='dark']) ...
```

Светлая тема часто задается через:

```css
:host(:not([data-color-mode='dark'])) ...
```

Если добавляется финальный override для светлой темы, нужно проверить, нужен ли аналогичный override для темной темы.

## CSS-организация

Файлы CSS большие и исторически накопленные. В них есть ранние базовые правила и поздние финальные переопределения.

Практическое правило:

- сначала искать существующий паттерн;
- не создавать новую структуру компонентов ради одного дизайна;
- новые правки добавлять точечно;
- финальные overrides допустимы, если нужно перебить старое правило без риска сломать большую часть файла;
- не использовать `!important`, если можно обойтись специфичностью и порядком правил.

В конце `style.css` каждого пространства есть блок `Final stability layer`. Его нужно держать последним. Он фиксирует правила, которые должны гарантированно победить старые накопленные стили: заголовки секций, строки каталога, размещение shortcut “Мои услуги”, usage overview, broadcast-карточки, положение счетчиков и фон quick-actions.

## Как безопасно создавать новый дизайн пространства

1. Скопировать существующее пространство целиком или начать от актуального эталонного пространства.
2. Сохранить весь HTML-состав без удаления секций и виджетов.
3. Менять визуальный стиль в `style.css`.
4. Не трогать Liquid-переменные, условия и циклы без отдельной задачи.
5. Не менять платформенные custom tags.
6. Не менять навигационные URL и `src` изображений без отдельной задачи.
7. Проверить светлую и темную тему.
8. Проверить desktop и mobile.
9. Сравнить, что набор ключевых секций и виджетов совпадает с другими пространствами.
10. После любой правки дизайна, верстки, токенов, тем или структуры секций актуализировать `DESIGN.md` сразу, без отдельного запроса пользователя.

Рабочее правило для агента: `DESIGN.md` является живой дизайн-докой проекта. Если меняется внешний вид, структура HTML/CSS, правила темы, токены или договоренности по поддержке пространств, нужно обновить документацию в том же проходе.

## Что нельзя делать

- Нельзя удалять элементы или виджеты в одном дизайне, чтобы он “смотрелся чище”.
- Нельзя делать разные пространства разными по функциональному составу.
- Нельзя автоматически заменять asset URL между пространствами.
- Нельзя удалять Liquid-условия и циклы без понимания данных платформы.
- Нельзя переименовывать платформенные custom tags.
- Нельзя изобретать новую HTML-структуру компонентов, если существующий паттерн уже есть.
- Нельзя править только одно пространство, если изменение касается общей верстки, логики или состава виджетов.

## Быстрые проверки

Проверить структуру:

```powershell
Get-ChildItem -Recurse -File
```

Проверить изображения и статические `img`:

```powershell
rg -n "selstorage|<img" "Беларусь ИТ/index.html" "ЦОД/index.html"
```

Проверить ключевые usage-стили:

```powershell
rg -n "rsvc-usage-widget|widgets--rsvc-usage" "Беларусь ИТ/style.css" "ЦОД/style.css"
```

Проверить, что HTML пространств не разошелся:

```powershell
git diff --no-index --stat -- "Беларусь ИТ/index.html" "ЦОД/index.html"
```

Проверить, что CSS может отличаться только визуально:

```powershell
git diff --no-index --stat -- "Беларусь ИТ/style.css" "ЦОД/style.css"
```

## Бейджи пространства

В текущих шаблонах бейдж пространства не используется. Унаследованный `Demo`-бейдж из старого проекта удален, потому что проект теперь работает с аккаунтами, а не demo/staging/prod-средами.

Правило на будущее:

- бейдж пространства можно использовать только если он нужен пользователю или администратору;
- бейдж не должен обозначать старую demo/staging/prod-среду;
- если бейдж остается, его текст должен соответствовать пространству, например `Беларусь ИТ` или `ЦОД`;
- бейдж не должен забирать клики у шапки и перекрывать контент на мобильных.

## Короткое резюме

Проект — это несколько визуальных дизайнов одного и того же портала для разных пространств: сейчас `Беларусь ИТ` и `ЦОД`.

HTML-состав, секции, виджеты, Liquid-логика и поведение должны оставаться одинаковыми.

Разные пространства отличаются только стилями и визуальной красотой.

Главный визуальный принцип: сохраняем весь функциональный состав, а индивидуальность аккаунта выражаем через аккуратную тему, палитру, поверхности, детали и поддержку светлой/темной темы.
